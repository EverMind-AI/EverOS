# LoCoMo 结果

EverOS 在 LoCoMo 上得分 **94.61%**，是用 `benchmarks/configs/locomo-step.toml` 跑 3 次 `agentic` 里最高的
一次。在下面这些模型上，`hybrid` 不调用 LLM，检索中位数 0.27 秒，分数最高 94.94；`agentic`
分数最高 95.78，用 `deepseek-v4.1-flash` 时 4.0 秒、95.52 分。总表之后的几节对比批量和
逐条边界检测，并拆开写入和检索耗时。想自己跑 LoCoMo，从 [README.zh.md](README.zh.md) 开始。

> English version: [locomo.md](locomo.md).

本文所有分数都按重判口径：LoCoMo 审计认为标准答案有误的 99 道题，按审计修正后的答案判分；见
[每次运行给出两个分数](README.zh.md#每次运行给出两个分数)。

  `Qwen/Qwen3-Reranker-4B`。`openai/gpt-4.1-mini` 是记忆系统发表 LoCoMo 分数时常用的模型，换用其他模型的分数

`gpt-5.4-mini` + `qwen3-235b` 高于 `qwen3-32b`（高 2.1）。两份分环节配置只有边界检测模型不同，差 0.5 个
百分点，这个差别不成立。

## batch 还是 step

两份 LoCoMo 配置只差两项 EverOS 设置，EverOS 的默认值是第一组：

| | `locomo`（默认） | `locomo-step` |
|---|---|---|
| 边界检测，`[boundary_detection] strategy` | `batch`：每次写入调用一次 | `step`：每条消息调用一次 |
| 回复格式，`[llm] response_format_mode` | `json_schema`：由服务商保证每条回复符合 schema | `prompt_only`：只在 prompt 里要求 schema |
| `agentic`，3 次运行取最高 | 94.35 | **94.61** |
| 每次运行的边界检测调用 | 544 次 | 约 5,250 次 |
| ADD 耗时（10 个 server） | 约 4 分钟 | 约 17–22 分钟 |
| 存下的 episode | 约 320 个 | 约 550 个 |
| agent 对话（含工具调用） | 支持 | 只处理对话消息 |

- **`locomo` 更快、更稳。** batch 的边界检测调用只有 step 的十分之一，写入快约 5 倍。strict 回复
  一定符合所要求的 schema；需要服务商支持 `json_schema`。
- **`locomo-step` 分数更高。** 它 `agentic` 的最高分比 batch 高 0.26 个百分点，在 LoCoMo 单次运行
  之间约 1 个百分点的波动以内。`prompt_only` 的回复解析不了时会重新请求。

做对话记忆、能接受较慢的写入时选 step；agent 场景和需要快速写入时保持默认。在 EverOS 部署里见
[`[boundary_detection]`](../docs/configuration.md#boundary_detection) 和
[`[llm]`](../docs/configuration.md#llm)。

各检索方式在两份配置建好的库上的分数：

| 检索方式 | 逐条边界检测（`locomo-step`） | 批量边界检测（`locomo`，默认） |
|---|---|---|
| `agentic` | **94.61** | 94.35 |
| `llm_multiround` | 94.29 | 94.29 |
| `hybrid` | **93.64** | 93.38 |
| `vector` | **92.73** | 92.08 |
| `keyword` | 91.04 | **92.27** |

加粗的是两份配置里较高的分数。每份配置的 `agentic` 跑 3 次取最高的一次，其余检索方式在那次运行建好的库上
各跑 1 次。`llm_multiround` 由一个 LLM decider 主导多轮检索，decider 用 `deepseek/deepseek-v4-flash-0731`
（关思考）；everalgo-core 0.7.0、everalgo-boundary 0.5.0。

## 写入耗时

一次写入要经过 4 个模型环节：边界检测判断一段对话在哪里结束；episode 抽取把这段对话写成一条 episode，
写进磁盘后请求才返回；summary 和原子事实（一句话一条的事实）随后在后台从 episode 里抽取。

每份配置写 3 段会话：LoCoMo 第 0、2、7 个对话各自的第一段会话（每段 16–18 条消息），每段都写进新库、用新
启动的 server；整段会话做一次 `/memory/add`，再做一次 `/memory/flush`，在客户端计时。每格是 3 段的中位数。

| 配置 | add | flush | add + flush | 全部抽取完成 |
|---|---|---|---|---|
| `deepseek-v4.1-flash` | 0.9 秒 | 3.1 秒 | 4.3 秒 | 10.3 秒 |
| `claude-haiku-5.5` | 2.3 秒 | 5.5 秒 | 7.8 秒 | 16.9 秒 |
| `gemini-2.5-flash-lite` | 1.1 秒 | 2.5 秒 | 3.6 秒 | 9.6 秒 |
| `qwen3-32b` | 1.5 秒 | 9.2 秒 | 10.9 秒 | 21.4 秒 |
| `gpt-5.4-mini` + `qwen3-235b` | 1.6 秒 | 4.1 秒 | 5.7 秒 | 46.0 秒† |
| `qwen3-4b` + `gpt-5.4-mini` + `qwen3-235b` | 1.4 秒 | 4.7 秒 | 6.0 秒 | 27.0 秒 |

† 单独测的，当时 `qwen/qwen3-235b-a22b-2507` 每次调用的耗时是测 `qwen3-4b` + `gpt-5.4-mini` + `qwen3-235b` 那份时的 2–3 倍（原子事实每次 34 秒对 18 秒），这个耗时反映的是服务商当时的速度。

- 每列各取各的中位数，所以 add 和 flush 加起来不等于 add + flush。
- **add** 做边界检测，批量检测每次 add 调用一次模型。这几段会话里 episode 是在 flush 时切出来的，所以
  **flush** 主要是抽取 episode 的那次调用。
- **全部抽取完成**：从 add 开始，到 summary 和原子事实也写完为止。这两个环节的模型只影响这一列。

已发表的配置逐条检测边界，每条消息调用一次模型，所以它的 add 按每条消息计时：

| 配置 | 每条消息的 add：一次边界检测调用 | flush | 全部抽取完成 |
|---|---|---|---|
| `gpt-4.1-mini`（已发表） | 1.3 秒 | 4.2 秒 | 38.9 秒 |

每条消息的 add 等待一次边界检测调用；这条消息结束一个 episode 时，再加上抽取 episode 的那次调用
（3.1 秒）。flush 和全部抽取完成是整段会话的耗时；一次 add 写入整段会话约需 22 秒，每条消息各调用
一次边界检测。

每段会话的耗时和每次模型调用的耗时见[附录](#每段会话的写入耗时)。LLM 走 OpenRouter，embedding 和重排走
DeepInfra，`qwen3-4b-instruct-2507` 用自部署的端点；换服务商或网络会改变这些数字。

## 检索耗时

每份配置在自己的 LoCoMo 库上检索：从第 0 个对话里抽 10 道题，每题 3 次，一次一个请求，服务商和写入相同；
结果见[上面的总表](#各模型和检索方式的分数与耗时)。

- `hybrid`、`vector`、`keyword` 不调用 LLM，耗时和模型无关：把所有配置的检索合在一起，每种方式各 210 次，
  中位数分别为 0.27 秒、0.25 秒和 0.01 秒，`hybrid` 和 `vector` 的耗时几乎都花在查询的 embedding 上。
- 一次 `agentic` 检索里 EverOS 自身只花约 0.1 秒，其余都是模型调用。每次检索至少调用一次 LLM，判断召回的
  记忆是否足够；进入第二轮时，再调用一次 LLM 生成补充查询，并再做一次重排。各类模型调用的耗时、90 分位
  和进入第二轮的比例见[附录](#检索耗时明细)。
