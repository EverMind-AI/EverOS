# Configuration

EverOS uses a two-file TOML configuration system with environment variable
overrides for container deployments.

## Quick Start

```bash
# 1. Generate config files in the default root (~/.everos/)
everos init

# 2. Edit the config — fill in API keys
$EDITOR ~/.everos/everos.toml

# 3. Start the server
everos server start
```

## Configuration Files

### `everos.toml` — Application Settings

Located at `<root>/everos.toml`. Controls all application behavior: API
bind address, LLM/embedding/rerank provider credentials, SQLite pragmas,
search strategy, memorize mode, and clustering tunables.

Generated by `everos init` from the shipped `config/default.toml`
template. Changes require a server restart.

### `ome.toml` — Strategy Configuration

Located at `<root>/ome.toml`. Controls the Offline Memory Engine (OME)
strategy scheduling: which strategies are enabled, cron expressions,
gate thresholds, and retry limits.

Generated by `everos init` from the shipped `config/default_ome.toml`
template. Changes are **hot-reloaded** within ~2 seconds — no server
restart needed.

### Source Priority

Settings are resolved in this order (later wins):

1. `config/default.toml` — shipped defaults (lowest priority)
2. `<root>/everos.toml` — user configuration (optional)
3. `EVEROS_*` environment variables — container/CI overrides
4. Programmatic init args (highest priority; internal use)

## Memory Root Resolution

The memory root directory is resolved from three sources (first wins):

| Source | Example |
|---|---|
| `--root` CLI flag | `everos server start --root /data/everos` |
| `EVEROS_ROOT` env var | `export EVEROS_ROOT=/data/everos` |
| Default | `~/.everos` |

All CLI commands that interact with storage accept `--root`:

```bash
everos server start --root /data/everos
everos cascade status --root /data/everos
everos config show --root /data/everos
everos init --root /data/everos
```

| `dim` | int | `1024` | No | Width of the `vector` column in every index table. See below. |
| `dimensions` | int | — | No | Server-side truncation width, passed through to the embedding API for models that support it (Matryoshka). Independent of `dim`. |
| `timeout_seconds` | float | `30.0` | No | Request timeout. |
| `max_retries` | int | `3` | No | Retry count on failure. |
| `batch_size` | int | `10` | No | Texts per batch request. |
| `max_concurrent` | int | `10` | No | Max parallel batch requests from write paths. |
| `query_max_concurrent` | int | `16` | No | Separate budget for interactive query embeds, so a search is not queued behind cascade writes. Each hybrid or vector search holds one slot for one embedding call, so the sustainable search rate is about this value divided by the endpoint's per-call latency; lower it if the endpoint is rate-limited. |

`timeout_seconds` bounds one request, and one request carries up to
`batch_size` texts (the cascade embeds a file's changed entries in one
batched call). On a slow or serialized local endpoint (CPU Ollama, a single
GPU) queued batch requests can exceed the timeout: lower `batch_size` and
`max_concurrent` together, or raise `timeout_seconds`.

#### Vector width (`dim`)

Every index table stores vectors in a fixed-width column, and `dim` is that
width. The model has to agree with it:

- **Model returns fewer dimensions than `dim`** — startup stops. Nothing could
  ever be stored, so there is no useful degraded mode. Set `dim` to what the
  model returns, then run `everos cascade rebuild`: the tables were already
  created at the old width.
- **Model returns more than `dim`** — the extra dimensions are **truncated on
  every write**, and startup warns once. This is lossless only for models
  trained for it (Matryoshka representation learning); with any other model
  recall degrades, because a plain prefix of an embedding is not a valid
  embedding. Either match `dim` to the model or use a Matryoshka model.

  **The shipped default is this case**: `Qwen/Qwen3-Embedding-4B` returns 2560
  dimensions and the default `dim` is 1024, so a default install sees this
  warning at every start. It is Matryoshka-trained, 1024 is one of its
  published truncation points, and the index compares with cosine distance, so
  nothing is lost. To silence it, set `dimensions = 1024` so the server returns
  the shorter vector — but only if your endpoint accepts that parameter; some
  self-hosted servers reject it outright, which is why it is not the default.
- **Changing `dim` on an existing index** — startup stops. Vectors of
  different lengths have no distance between them, so there is nothing to
  migrate: `everos cascade rebuild` re-embeds from markdown.

- **Downgrading after changing `dim`** — an older EverOS hardcodes 1024, so it
  refuses to start against a wider or narrower index (`schema drift:
  type_drift=[...]`), and its `cascade rebuild` rebuilds at 1024 without
  mentioning it. Set `dim` back to 1024 and rebuild *before* downgrading, or
  expect to rebuild afterwards.

`dimensions` is a different knob: it asks the *server* to truncate (with
re-normalisation, which is why it is preferable when the model supports it).
Tables are still built at `dim`. If both are set and they disagree, startup
warns and names both values.

The width is measured by one embedding call at startup, with a **5-second
budget and no retries** — it buys a single integer and sits in front of every
`everos` command, so it does not inherit `timeout_seconds` × `max_retries`. A
model that is still loading (a cold local endpoint) can miss that budget: the
width check is then skipped for that start, the tables are created at `dim`,
and `/health` reports `embed: false` until the next restart. Start the model
first, or restart once it is up.

#### Changing the embedding model

An index remembers which model built it, and startup refuses to open one
built by a different model -- distances between vectors from two models are
meaningless, and the failure is otherwise silent: searches simply return
nothing useful. The recovery is `everos cascade rebuild`, which re-embeds
every entry from markdown and records the new model.

Deployments with no embedding configured (no `api_key`, for instance) are
unaffected: nothing is probed, compared, or recorded.

| Field | Type | Default | Description |
|---|---|---|---|
| `enabled` | bool | `true` | Off: new `async_mode` requests run synchronously; rows accepted while on are still delivered, and their sessions keep the ordering rule. |

| `retry_backoff_seconds` | float | `2.0` | Pause between attempts. |

### `[cascade]`

[cascade_runbook.md](cascade_runbook.md)). Requires restart.

| Field | Type | Default | Description |
|---|---|---|---|

| `optimize_prune_retention_seconds` | float | `60.0` | Versions replaced longer ago than this become eligible for deletion. |
| `optimize_rebuild_interval_seconds` | float | `43200.0` | Full index rebuild per kind (12 h), collapsing the index fragments every optimize grows. |
| `scan_interval_seconds` | float | `30.0` | How often the scanner walks the memory root for changes the watcher missed; on a mount without filesystem events this is the edit-to-searchable latency. |

## Troubleshooting

Use `everos config show` to inspect the effective configuration:

```bash
everos config show
everos config show --root /data/everos
```

This prints:
- The resolved root directory
- Which config files were found
- All settings sections with their effective values
- API keys are masked in output

### First start downloads the token-counting encoding

The algorithm library counts tokens with tiktoken's `o200k_base` encoding.
tiktoken downloads it (about 1.7 MB) the first time a machine uses it and
caches it in `TIKTOKEN_CACHE_DIR` (default: a `data-gym-cache` folder under
the temp directory). `everos server start` loads the encoding before it
opens any storage, so a host that cannot download it stops at startup with
`TokenizerAssetError` instead of failing the first agent `/add`. For an
offline host, copy the cache folder from a machine that has it and point
`TIKTOKEN_CACHE_DIR` at the copy.

## Advanced: Container Deployment

In containerized environments, skip `everos init` and use environment
variables directly:

```dockerfile
ENV EVEROS_ROOT=/data/everos
ENV EVEROS_LLM__API_KEY=sk-...
ENV EVEROS_LLM__MODEL=gpt-4o
ENV EVEROS_EMBEDDING__MODEL=text-embedding-3-large
ENV EVEROS_EMBEDDING__API_KEY=sk-...
ENV EVEROS_EMBEDDING__BASE_URL=https://api.openai.com/v1
ENV EVEROS_API__HOST=0.0.0.0
ENV EVEROS_API__PORT=8000
```

Environment variable naming convention:

```
EVEROS_<SECTION>__<KEY>
```

- Section and key are uppercased
- Double underscore (`__`) separates section from key
- Nested sections use additional `__` separators

Examples:

| TOML | Environment Variable |
|---|---|
| `[llm] api_key = "sk-..."` | `EVEROS_LLM__API_KEY=sk-...` |
| `[sqlite] busy_timeout_ms = 10000` | `EVEROS_SQLITE__BUSY_TIMEOUT_MS=10000` |
| `[memory] timezone = "Asia/Tokyo"` | `EVEROS_MEMORY__TIMEZONE=Asia/Tokyo` |


### Multi-round search configuration reads

Multi-round search uses an explicit configuration source. Base `[decider]`
settings retain the application settings cache; changing ordinary settings
requires the existing cache invalidation/reload path. Legacy `EVEROS_LLMMR_*`
overrides still take precedence and are read on each configuration-source call.
Blank overrides are ignored; malformed numeric overrides log a warning and
retain the configured value. `EVEROS_LLMMR_TRACE_DUMP` is also read dynamically.

The source is consulted at the existing loop, candidate-rendering, decider and
final-selection boundaries. It is not a startup snapshot or a uniform
per-request snapshot. Application assembly passes the readers explicitly;
standalone search and decider calls retain their existing environment-backed
behavior when the optional reader arguments are omitted. This internal change
does not change configuration defaults or retry behavior.
