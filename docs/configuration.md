# Configuration

EverOS uses a two-file TOML configuration system with environment variable
overrides for container deployments.

## Quick Start

```bash
# 1. Generate config files in the default root (~/.everos/)
everos init

# 2. Edit the config — fill in API keys
$EDITOR ~/.everos/everos.toml

# 3. Start the server
everos server start
```

## Configuration Files

Linux CLI processes use a default glibc arena limit of two. This is configured
before interpreter startup, outside the TOML/`.env` settings below. See
[Linux allocator default](cli.md#linux-allocator-default) for overrides and
direct Uvicorn/Python usage.

### `everos.toml` — Application Settings

Located at `<root>/everos.toml`. Controls all application behavior: API
bind address, LLM/embedding/rerank provider credentials, SQLite pragmas,
search strategy, memorize mode, and clustering tunables.

Generated by `everos init` from the shipped `config/default.toml`
template. Changes require a server restart.

### `ome.toml` — Strategy Configuration

Located at `<root>/ome.toml`. Controls the Offline Memory Engine (OME)
strategy scheduling: which strategies are enabled, cron expressions,
gate thresholds, and retry limits.

Generated by `everos init` from the shipped `config/default_ome.toml`
template. Changes are **hot-reloaded** within ~2 seconds — no server
restart needed.

### Source Priority

Settings are resolved in this order (later wins):

1. `config/default.toml` — shipped defaults (lowest priority)
2. `<root>/everos.toml` — user configuration (optional)
3. `EVEROS_*` environment variables — container/CI overrides
4. Programmatic init args (highest priority; internal use)

## Memory Root Resolution

The memory root directory is resolved from three sources (first wins):

| Source | Example |
|---|---|
| `--root` CLI flag | `everos server start --root /data/everos` |
| `EVEROS_ROOT` env var | `export EVEROS_ROOT=/data/everos` |
| Default | `~/.everos` |

All CLI commands that interact with storage accept `--root`:

```bash
everos server start --root /data/everos
everos cascade status --root /data/everos
everos config show --root /data/everos
everos init --root /data/everos
```

### `[tokenizer]`

The keyword (BM25) tokenizer. Indexing and search share one instance, because
the stored token columns only match queries tokenized the same way: changing
`name` requires rebuilding the index (`everos cascade rebuild`).

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | `"jieba"` | `jieba`: mixed Chinese / English text. `nltk`: the keyword pipeline of the EverAlgo LoCoMo harness (lowercase, NLTK `word_tokenize`, alphabetic tokens of two or more characters, NLTK English stopwords, Porter stemming); English only, and digits never become tokens. |

`nltk` needs the optional package and its data, and downloads nothing at
runtime; a missing piece stops startup with the command that installs it:

```bash
pip install "everos[nltk]"
python -m nltk.downloader punkt_tab stopwords
```

The LanceDB keyword index lowercases, Snowball-stems and ASCII-folds tokens on
both the indexed and the query side, so on that backend `nltk` tokens are
stemmed a second time; matching stays symmetric.

### `[llm]`

| Field | Type | Default | Required | Description |
|---|---|---|---|---|
| `model` | string | `"gpt-4.1-mini"` | No | LLM model identifier. |
| `api_key` | string | — | **Yes** | API key for the LLM provider. |
| `base_url` | string | — | No | Custom endpoint URL (OpenAI-compatible). |
| `timeout_seconds` | float | `60.0` | No | Deadline of one request. One add or flush may spend up to `(invalid_reply_retries + 1) × timeout_seconds` per extraction call plus the client's own retries, so size reverse-proxy and client timeouts accordingly; raise it for slow self-hosted endpoints. |
| `invalid_reply_retries` | int | `1` | No | Extra attempts of the identical request after a reply that fails validation. |
| `response_format_mode` | string | `"json_schema"` | No | How the reply format is requested: `json_schema` (strict schema), `json_object` (JSON mode) or `prompt_only`. |

| `max_tokens` | int | unset | No | Output cap sent only when a call names none; unset, the request carries none. A reasoning model bills its thinking against it. |
| `sdk_max_retries` | int | unset | No | Transport retries inside the OpenAI SDK; unset keeps the SDK default. They multiply with `invalid_reply_retries`. |

`[llm]` is the only LLM section you need: every task below uses it unless its
own section says otherwise. `[llm]` and its task sections reject unknown keys
-- a typo fails startup with the list of valid names, instead of being ignored
while the task quietly keeps `[llm]`'s model.

### `[llm.<task>]`

Each place EverOS calls an LLM is a *task*. An optional `[llm.<task>]` section
sets any `[llm]` field for that one task.

**Inheritance, one rule:** each field is decided on its own. A field the task
section sets is used; a field it leaves out comes from `[llm]`. So a section
that names only `model` keeps `[llm]`'s endpoint, key and `extra`. `extra` is
one value: written, it replaces `[llm].extra` whole -- never merged key by key,
because a key meant for one gateway can be rejected by another, and a merge
would carry it across silently. A blank `model`, `api_key` or `base_url`
inherits too, so a template's `api_key = ""` cannot mask `[llm]`'s key.

| Task | What it calls the model for |
|---|---|
| `boundary` | Cutting a session's messages into memcells (user and agent tracks) |
| `episode` | Extracting each memcell's episode |
| `summary` | The episode's display summary, a separate call made beside `episode` |
| `atomic_fact` | Atomic-fact extraction |
| `foresight` | Foresight extraction |
| `profile` | User-profile extraction |
| `reflection` | Episode reflection |
| `agent_case` | Agent-case extraction, and the case gate when `[agent_memory] case_gate_enabled` |
| `agent_skill` | Agent-skill extraction and skill clustering |
| `knowledge` | Topic extraction from uploaded knowledge documents |
| `search` | Search-time calls: agentic retrieval and the LLM rerank lane |
| `decider` | The multi-round retrieval decider (`llm_multiround`) |

The task names are a stable interface. Environment variables nest one more
level: `EVEROS_LLM__<TASK>__<FIELD>`, e.g. `EVEROS_LLM__BOUNDARY__MODEL`.
`everos config show` prints what every task resolves to -- model, endpoint host
and the section each field came from -- and the server logs the same at
startup (`llm.task.resolved`; the key is never printed).

**The decider's own defaults.** The decider runs inside a search request, so
the time and retry budget of one round is bounded by the caller waiting on it,
not by `[llm]`'s background-extraction values. These three fields, when
`[llm.decider]` leaves them unset, take the decider's own values instead of
`[llm]`'s:

| Field | Decider default | Why |
|---|---|---|
| `timeout_seconds` | `60.0` | A slow extraction endpoint must not stretch every search round. |
| `sdk_max_retries` | `0` | `[decider] retries` already retries; SDK retries would multiply with it. |
| `invalid_reply_retries` | `1` | A raised `[llm]` value does not carry over: `[decider] retries` already covers an unusable reply. |

Every other decider field inherits `[llm]` like any task. The decider always
gets a client of its own; tasks that resolve to the same settings share one.

**Deprecated: the LLM keys of `[decider]`.** `[decider]` keeps the multi-round
loop tuning (`max_rounds`, `seed_topk`, ...). Its former LLM keys -- `model`,
`api_key`, `base_url`, `timeout_seconds`, `extra`, `max_tokens`,
`sdk_max_retries`, `response_format_mode`, `invalid_reply_retries`, and their
`EVEROS_DECIDER__*` variables -- are still read: each one set applies to the
decider unless `[llm.decider]` sets the same field, and startup logs a
deprecation warning. Move them to `[llm.decider]` (`EVEROS_LLM__DECIDER__*`).

#### Recipes

One model for everything -- configure `[llm]` only:

```toml
[llm]
model = "openai/gpt-4.1-mini"
api_key = "sk-..."
base_url = "https://openrouter.ai/api/v1"
```

A cheaper model for boundary detection, the strong one for everything else:

```toml
[llm]
model = "openai/gpt-4.1-mini"
api_key = "sk-..."
base_url = "https://openrouter.ai/api/v1"

[llm.boundary]
model = "openai/gpt-4.1-nano"
```

A reasoning model for the profile (recommended). The everalgo profile
evaluation ran `claude-haiku-5-5` with thinking on at its default effort, at
about 28s median and 41s p90 per call, so give it a longer deadline than
`[llm]`'s 60s; switch thinking on through `extra` as your gateway names it and
leave the effort at the gateway's default:

```toml
[llm.profile]
model = "<a reasoning model>"
timeout_seconds = 240.0
```

Keep private extraction on a local endpoint (the section names its own
endpoint and key; nothing else changes):

```toml
[llm.profile]
model = "qwen3-32b"
base_url = "http://localhost:8000/v1"
api_key = "local"

[llm.atomic_fact]
model = "qwen3-32b"
base_url = "http://localhost:8000/v1"
api_key = "local"
```

Force a request field on every task -- set it once in `[llm]`; each task
inherits it unless it writes its own `extra`, which replaces it:

```toml
[llm]
extra = { extra_body = { chat_template_kwargs = { enable_thinking = false } } }

[llm.search]                       # another gateway, which rejects that field
model = "gpt-4.1-mini"
base_url = "https://api.openai.com/v1"
api_key = "sk-..."
extra = {}
```

### `[profile]`

User-profile extraction: how many episodes one call folds. Its LLM is `[llm.profile]` (see the recipes above).

Episodes are folded one owner at a time. A run folds the episode that triggered it together with that owner's newer episodes still waiting (up to `max_episodes_per_call` in all), and the runs of those episodes then end without a call. A burst of episodes for one owner, such as a bulk import, therefore drains in about `1 / max_episodes_per_call` of the calls, and runs queued behind a slow model stay within `[ome] run_timeout_seconds`.

| Field | Type | Default | Required | Description |
|---|---|---|---|---|
| `max_episodes_per_call` | int | `10` | No | Most episodes one extraction call folds, the triggering one included; `1` folds each alone. |

| `dim` | int | `1024` | No | Width of the `vector` column in every index table. See below. |
| `dimensions` | int | — | No | Server-side truncation width, passed through to the embedding API for models that support it (Matryoshka). Independent of `dim`. |
| `timeout_seconds` | float | `30.0` | No | Request timeout. |

`timeout_seconds` bounds one request, and one request carries up to
`batch_size` texts (the cascade embeds a file's changed entries in one
batched call). On a slow or serialized local endpoint (CPU Ollama, a single
GPU) queued batch requests can exceed the timeout: lower `batch_size` and
`max_concurrent` together, or raise `timeout_seconds`.

#### Vector width (`dim`)

Every index table stores vectors in a fixed-width column, and `dim` is that
width. The model has to agree with it:

- **Model returns fewer dimensions than `dim`** — startup stops. Nothing could
  ever be stored, so there is no useful degraded mode. Set `dim` to what the
  model returns, then run `everos cascade rebuild`: the tables were already
  created at the old width.
- **Model returns more than `dim`** — the extra dimensions are **truncated on
  every write**, and startup warns once. This is lossless only for models
  trained for it (Matryoshka representation learning); with any other model
  recall degrades, because a plain prefix of an embedding is not a valid
  embedding. Either match `dim` to the model or use a Matryoshka model.

  **The shipped default is this case**: `Qwen/Qwen3-Embedding-4B` returns 2560
  dimensions and the default `dim` is 1024, so a default install sees this
  warning at every start. It is Matryoshka-trained, 1024 is one of its
  published truncation points, and the index compares with cosine distance, so
  nothing is lost. To silence it, set `dimensions = 1024` so the server returns
  the shorter vector — but only if your endpoint accepts that parameter; some
  self-hosted servers reject it outright, which is why it is not the default.
- **Changing `dim` on an existing index** — startup stops. Vectors of
  different lengths have no distance between them, so there is nothing to
  migrate: `everos cascade rebuild` re-embeds from markdown.

- **Downgrading after changing `dim`** — an older EverOS hardcodes 1024, so it
  refuses to start against a wider or narrower index (`schema drift:
  type_drift=[...]`), and its `cascade rebuild` rebuilds at 1024 without
  mentioning it. Set `dim` back to 1024 and rebuild *before* downgrading, or
  expect to rebuild afterwards.

`dimensions` is a different knob: it asks the *server* to truncate (with
re-normalisation, which is why it is preferable when the model supports it).
Tables are still built at `dim`. If both are set and they disagree, startup
warns and names both values.

The width is measured by one embedding call at startup, with a **5-second
budget and no retries** — it buys a single integer and sits in front of every
`everos` command, so it does not inherit `timeout_seconds` × `max_retries`. A
model that is still loading (a cold local endpoint) can miss that budget: the
width check is then skipped for that start, the tables are created at `dim`,
and `/health` reports `embed: false` until the next restart. Start the model
first, or restart once it is up.

#### Changing the embedding model

An index remembers which model built it, and startup refuses to open one
built by a different model -- distances between vectors from two models are
meaningless, and the failure is otherwise silent: searches simply return
nothing useful. The recovery is `everos cascade rebuild`, which re-embeds
every entry from markdown and records the new model.

Deployments with no embedding configured (no `api_key`, for instance) are
unaffected: nothing is probed, compared, or recorded.

### `[boundary_detection]`

| Field | Type | Default | Description |
|---|---|---|---|
| `strategy` | string | `"batch"` | `batch`: one model call per add cuts the whole buffer. `step`: one model call per message decides whether it starts a new episode; chat messages only, so use it with `[memorize] mode = "chat"`. |
| `hard_token_limit` | int | `65536` | `batch` only: max tokens before a forced boundary. |
| `hard_msg_limit` | int | `500` | `batch` only: max messages before a forced boundary. |

`step` keeps everalgo's own step limits; every other cutting parameter is
everalgo's `BoundaryDetector` default.

**Choosing a strategy.** `batch` is faster; `step` scored higher on LoCoMo. Keep
`batch` unless slower ingest is worth it for chat memory:

| | `batch` (default) | `step` |
|---|---|---|
| Boundary calls | one per add (544 for all of LoCoMo) | one per message (about 5,250 for LoCoMo) |
| LoCoMo ingest, 10 servers | about 4 minutes | about 17–22 minutes |
| Episodes stored for LoCoMo | about 320 | about 550, each shorter |
| Agent conversations (tool calls) | supported | chat messages only |
| LoCoMo `agentic`, best of three runs | 94.35%\* | 94.61%\* |

The two scores are within LoCoMo's run-to-run spread of about one point. They
were measured with the reply format of each benchmark config: `batch` with the
default `[llm] response_format_mode = "json_schema"`, which keeps every reply to
its schema, and `step` with `"prompt_only"` for every call
([benchmarks/README.md](../benchmarks/README.md#batch-or-step)).

\* Graded against the corrected answers of the LoCoMo gold audit for the 99
questions it disputes.

### `[memorize.async_queue]`

(see [api.md](api.md#asynchronous-mode)).

| Field | Type | Default | Description |
|---|---|---|---|
| `enabled` | bool | `true` | Off: new `async_mode` requests run synchronously; rows accepted while on are still delivered, and their sessions keep the ordering rule. |

| `max_pending_per_session` | int | `50` | Unfinished batches per session; beyond this `/add` and `/flush` answer `429`. |
| `max_pending_total` | int | `200` | Unfinished batches across all sessions; beyond this the answer is `429`. |
| `max_payload_bytes` | int | `4194304` | One serialised request body; beyond this the answer is `413`. |
| `scan_interval_seconds` | float | `5.0` | Fallback sweep interval; an enqueue wakes the worker immediately. |
| `max_attempts` | int | `1` | Delivery attempts per batch before it is marked `failed` and skipped. Keep `1` unless duplicate memcells after a partial failure are acceptable: the pipeline is not atomic. |
| `boundary_max_attempts` | int | `3` | Attempts for a boundary LLM failure only. It runs before the memcell/buffer write, so retrying it cannot duplicate state; other failures still use `max_attempts`. |
| `retry_backoff_seconds` | float | `2.0` | Pause between attempts. |
| `max_replays` | int | `3` | A batch in flight when the process died is replayed on the next start; after this many replays without finishing it is marked `failed` (`error_code: replays_exhausted`). |
| `row_retention_hours` | float | `168.0` | Rows of any status are deleted this long after creation (seven days), including rows never delivered; the purge logs a warning for those. Delivered rows drop their request body at once, `failed` rows keep it. |

### `[cascade]`

The cascade projects the markdown truth into the search index (see
[cascade_runbook.md](cascade_runbook.md)). Requires restart.

| Field | Type | Default | Description |
|---|---|---|---|
| `enabled` | bool | `true` | Run the cascade (watcher + scanner + worker) in the server. Off: md edits never become searchable — only for runs that never search, or that drive `everos cascade sync` themselves. |
| `watcher_enabled` | bool | `true` | Run the filesystem watcher. Off: the scanner alone picks up md edits, one `scan_interval_seconds` later. For a host whose inotify watch limit is exhausted (the server would otherwise die at startup with `Errno 28`); unlike `enabled = false`, md still reaches the index. |
| `optimize_heartbeat_seconds` | float | `60.0` | Idle sweep offering every kind to the optimizer, so an unindexed tail left by a crash is merged without new writes. |
| `optimize_prune_interval_seconds` | float | `300.0` | How often superseded dataset versions are reclaimed. |
| `optimize_prune_retention_seconds` | float | `60.0` | Versions replaced longer ago than this become eligible for deletion. |
| `optimize_rebuild_interval_seconds` | float | `43200.0` | Full index rebuild per kind (12 h), collapsing the index fragments every optimize grows. |
| `scan_interval_seconds` | float | `30.0` | How often the scanner walks the memory root for changes the watcher missed; on a mount without filesystem events this is the edit-to-searchable latency. |
| `delete_fence_warn_entries` | int | `100000` | A memory deletion keeps the index rows it removed from being written back by cascade runs that started before it, until those runs end; holding more entries than this logs `memory_delete_fence_large` (some run is not ending). Gauges: `everos_memory_delete_fence_entries`, `everos_memory_delete_fence_runs`. |

### `[ome]`

Engine-wide tunables of the Offline Memory Engine. Distinct from
[`ome.toml`](#ometoml--strategy-configuration), which overrides individual
strategies and is hot-reloaded; these require a restart.

| Field | Type | Default | Description |
|---|---|---|---|
| `max_concurrent_runs` | int | `20` | Cap on concurrent strategy runs. Each slot mostly waits on a remote extraction call, so a bulk ingest can afford far more. |

### `[purge]`

Online clearing ([`POST /api/v2/memory/purge`](api.md#post-apiv2memorypurge)).
A purge blocks nothing; it waits for the work that was in flight when it
was confirmed before it deletes a second time, and these bound how long a
job can take.

| Field | Type | Default | Description |
|---|---|---|---|
| `run_budget_seconds` | float | `7200.0` | Total running time of one purge across retries, its wait for in-flight work included; past it the job ends `failed`. Time the server is stopped or the machine sleeps is not counted. |

| `count_timeout_seconds` | float | `30.0` | Per-store limit on counting the summary; a slower store reads `null` and the summary says `complete: false`. |

## Troubleshooting

Use `everos config show` to inspect the effective configuration:

```bash
everos config show
everos config show --root /data/everos
```

This prints:
- The resolved root directory
- Which config files were found
- All settings sections with their effective values
- API keys are masked in output

### First start downloads the token-counting encoding

The algorithm library counts tokens with tiktoken's `o200k_base` encoding.
tiktoken downloads it (about 1.7 MB) the first time a machine uses it and
caches it in `TIKTOKEN_CACHE_DIR` (default: a `data-gym-cache` folder under
the temp directory). `everos server start` loads the encoding before it
opens any storage, so a host that cannot download it stops at startup with
`TokenizerAssetError` instead of failing the first agent `/add`. For an
offline host, copy the cache folder from a machine that has it and point
`TIKTOKEN_CACHE_DIR` at the copy.

## Advanced: Container Deployment

In containerized environments, skip `everos init` and use environment
variables directly:

```dockerfile
ENV EVEROS_ROOT=/data/everos
ENV EVEROS_LLM__API_KEY=sk-...
ENV EVEROS_LLM__MODEL=gpt-4o
ENV EVEROS_EMBEDDING__MODEL=text-embedding-3-large
ENV EVEROS_EMBEDDING__API_KEY=sk-...
ENV EVEROS_EMBEDDING__BASE_URL=https://api.openai.com/v1
ENV EVEROS_API__HOST=0.0.0.0
ENV EVEROS_API__PORT=8000
```

Environment variable naming convention:

```
EVEROS_<SECTION>__<KEY>
```

- Section and key are uppercased
- Double underscore (`__`) separates section from key
- Nested sections use additional `__` separators

Examples:

| TOML | Environment Variable |
|---|---|
| `[llm] api_key = "sk-..."` | `EVEROS_LLM__API_KEY=sk-...` |
| `[llm.boundary] model = "openai/gpt-4.1-nano"` | `EVEROS_LLM__BOUNDARY__MODEL=openai/gpt-4.1-nano` |
| `[sqlite] busy_timeout_ms = 10000` | `EVEROS_SQLITE__BUSY_TIMEOUT_MS=10000` |
| `[memory] timezone = "Asia/Tokyo"` | `EVEROS_MEMORY__TIMEZONE=Asia/Tokyo` |


### Multi-round search configuration reads

Multi-round search uses an explicit configuration source. Base `[decider]`
settings retain the application settings cache; changing ordinary settings
requires the existing cache invalidation/reload path. Legacy `EVEROS_LLMMR_*`
overrides still take precedence and are read on each configuration-source call.
Blank overrides are ignored; malformed numeric overrides log a warning and
retain the configured value. `EVEROS_LLMMR_TRACE_DUMP` is also read dynamically.

The source is consulted at the existing loop, candidate-rendering, decider and
final-selection boundaries. It is not a startup snapshot or a uniform
per-request snapshot. Application assembly passes the readers explicitly;
standalone search and decider calls retain their existing environment-backed
behavior when the optional reader arguments are omitted. This internal change
does not change configuration defaults or retry behavior.
